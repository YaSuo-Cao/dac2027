# 闭环预算扩展：讨论稿，尚未启动模型或仿真

目前锁定的 Fast 是最多一次代码修复，Full 是最多两次代码修复；不得把现有结果追溯改称五轮结果。闭环系统有必要报告随预算增长的恢复曲线，但不要求每个实例强制修复五次。

## 预算与公平比较

- 保持同一 168 题 × 5 HCL = 840 实例、同一模型、冻结初始候选、接口路由和官方评测指纹。
- 分别报告最多 R=0,1,2,3,4,5 次修复的完整 /840 结果。初始生成也占一次代码调用，因此代码预算 B=1+R。
- 对 Pass@5 / G(P)-Gated Best-of-5 的等代码调用比较使用 B=5，即初始生成加最多四次修复；R=5 对应 B=6，单列展示。
- 代码调用上限相同不代表总调用或 Token 预算相同。单独报告代码调用、包含契约及格式纠正的全部模型调用、真实输入/输出 Token、五语言共享与单语言按需契约账单、评测时间。若声称等 Token 预算，必须另行预冻结共同 Token 上限及预算耗尽规则。
- 继续使用实验三的同分布五样本统计；Pass@k 是借助事后功能标签计算的 oracle any-pass 指标，Best-of-k 才是盲门控实际选择的指标，两者不可混称。
- 自适应闭环报告实际累计成功率或 Success@B，不套用独立同分布样本的 Pass@k 估计公式。每轮反馈改变下一次请求，因此不是独立采样。
- 另外报告 G(P)、Q_native 和 C_RTL 的实际调用次数及耗时。闭环使用功能反例作为反馈，Best-of-k 在选择阶段不读取 Q_native；两者的信息条件须说明，不能只对齐 LLM 调用数就声称所有资源相同。

## 迭代语义与停止条件

1. 对所有实例先评估冻结初始候选。Q_native 已通过则提前停止，不强制增加修复。
2. C0 未通过时提供当前编译异常走 FL；C0 通过而 Q_native 失败时提供当前反例，并按公开 clk 端口及规格词走 FTL/FCL/FCTL。
3. 仅在第一次实际需要契约时生成 C(x)，此后复用；契约仍失败的实例保留在分母、收取所有尝试成本，按冻结的失败策略结束该分支。
4. 修复候选通过 C0 才可替换已接受候选。若修复被构造门控拒绝，下一轮可修复该拒绝源码及其新编译异常，原已接受候选作为回退；不得重发完全相同请求并把缓存命中计作一次独立迭代。
5. 在 Q_native 成功、预算耗尽或预先规定的无进展条件满足时结束。重复源码/重复反馈的停止规则须在启动前固定，不能按结果调整。
6. 现有闭环以 Q_native 成功早停，C_RTL 作为独立最终验收。将 RTL 失败也反馈给模型属于另一种 RTL-aware 协议，必须单列，不可合入原 Full 结果。

## 输出与统计

每轮保存 request/response/source 的哈希、父候选、失败证据、路由分支、是否接受、停止原因、调用/Token/耗时及全部传输重试。工程与网络失败按原请求重试，不占一个新的语义修复轮次，相关实际成本另记；固定输出预算内的模型截断、语法及行为错误保留为结果。

主表报告每个 R/B 的 C0、Q_native、C_RTL、每轮新增恢复数、实际平均调用和成本。与 Best-of-5 做按 168 个题目聚类的配对差异、Bootstrap 95% CI 与置换检验；多预算比较固定校正族。不得预设五轮一定优于采样，应如实报告收益是否饱和及哪些失败持续存在。
